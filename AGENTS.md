Это Pointman: нативный движок порта F.E.A.R. на Linux (Android позже). Цель — кампания + XP/XP2 **один в один** по картинке, геймплею и ИИ. Свой Vulkan-бэкенд, не DXVK и не ремейк с PBR.

Для картинки, света, неба и «видно ли баг на экране» используй kwin MCP **только в live-режиме** — реальное окно на GPU, не виртуальный KWin.

- Сервер: `kwin-mcp --default-live-session` в `.cursor/mcp.json`. Операционный цикл: skill `pointman-kwin-live`.

## Что нельзя нарушать

- Ассеты в репозиторий не кладём. Нужна легальная F.E.A.R. Ultimate Shooter Edition (Steam `21090`). `reztool extract` — только для своей копии, не для публикации данных.
- Это не слив LithTech и не пиратский клиент. Форматы — публичный SDK 1.08 и community-спеки.
- Порядок фаз жёсткий (`ROADMAP.md`): сначала картинка Intro 1:1, потом игрок 1:1 (slow-mo, оружие, HUD), потом скрипты, ИИ, системы, кампания. Не закрываем фазу «на глаз». Ходьба/обзор — камера для сверки кадра, не закрытая фаза игрока.
- Lighting model — Jupiter EX (Blinn-Phong, лампы мира, stencil shadow volumes). Не тащим clustered/SSAO/TAA/PBR «для красоты».
- Геймпад по умолчанию — схема Xbox 360 SKU, не раскладка современного шутера.
- PhysicsBSP — для ног, не вторая стена в кадре. WorldModel-болванки не должны наезжать на запечённые стены.

## Правила написания тестов

Обязательно пиши тесты на проверку работоспособности функционала, а не только на хелперы или внутренние стадии. Примеры для этого проекта:
- не только «заголовок World00p прочитался», а `Simulation::tick` + `draw_list()` отдаёт поверхности/свет/камеру;
- не только «DDS распарсился», а cubemap не пролезает как плоская текстура стены, материал попадает в слот;
- не только «GOAP собрал план», а цель выбирается с приоритетом (combat бьёт patrol).

Синтетические байты и геометрия — норма для unit-тестов. Тесты, которые читают розничный Steam-install, только за опциональным путём/env и не в CI по умолчанию. CI сейчас: `cargo test -p pointman-ai -p pointman-assets -p pointman-game` (нужен `glslc` для render). Визуальный 1:1 — ручная сверка, пока нет автосравнения скринов.

## Обязательная разгрузка исследования

Основной агент обязан беречь свой контекст для требований пользователя, архитектурных решений, реализации и финальной проверки. Широкое исследование репозитория по умолчанию отдаём read-only субагенту: project-scoped `luna_worker` из `.codex/agents/luna_worker.toml`, если он есть; иначе Cursor `explore` / другой read-only субагент с тем же bounded-заданием. Молча переходить к широкому самостоятельному исследованию запрещено.

Перед самостоятельным широким чтением или поиском сначала делегировать отдельную bounded-задачу, если заранее не известны точные файлы, символы и полный путь зависимостей. Это обязательно для:
- первичного картирования незнакомого участка проекта;
- поиска владельцев состояния, boundary/API, реализаций и ссылок;
- инвентаризации связанных тестов, fixtures, diagnostics и проверочных команд;
- анализа длинных логов, больших diff и повторяющихся ошибок;
- независимого поиска test gaps, edge cases и возможных нарушений инвариантов;
- сверки нескольких модулей или crate-ов перед изменением архитектурной границы.

Для независимых направлений исследования запускать отдельные bounded-задачи параллельно, пока это укладывается в лимит субагентов. Нельзя поручать двум субагентам запись в пересекающиеся файлы; исследователь всегда read-only.

После handoff основной агент не должен повторять широкое исследование и загружать те же файлы целиком. Он читает только указанные точные символы, ссылки и небольшие фрагменты, необходимые для проверки высокорисковых выводов или устранения противоречий.

 ## Архитектурные правила для новых фич

 Проект уже не прототип. Новые фичи пишем так, чтобы систему можно было точечно расширять, тестировать и чинить без переписывания соседних модулей.

 Эти правила применяются ко всем частям проекта: `apps/pointman`, `crates/engine`, `crates/render`, `crates/assets`, `crates/game`, `crates/ai`, `apps/reztool` и будущим модулям. Контракт кадра `Simulation::tick` → `Simulation::draw_list()` → `Renderer::draw` — пример подхода, а не исключение.


 1. Модуль владеет своими данными и инвариантами. Внешний код не должен читать/менять внутренние поля напрямую, если это можно выразить через осмысленный internal API.

 2. Internal API должен описывать намерение, а не устройство хранения. Хорошо: `ClipMesh::eye_fits()`, `WorldModels::physics()`, `GameMount::read_world()`, `Simulation::draw_list()`. Плохо: проверки конкретного поля из другого модуля ради удобства.

 3. Не связываем модули знанием конкретной реализации. `apps/pointman`, `engine`, `render`, `assets` и `game` должны зависеть от контрактов и boundary methods, а не от того, какой именно Vulkan-объект, очередь, BSP-поле или thread сейчас внутри.

 4. Ownership и lifecycle держим на правильном уровне. Не прячем важные решения о владении GPU-ресурсами, mesh/texture ids, generation, коллизии vs отрисовке или учёте света внутрь “удобного” метода, если это меняет ответственность слоя.

 5. Если новая фича требует прямого доступа к чужому полю, сначала считаем это архитектурным запахом. Либо добавляем маленький метод у владельца состояния, либо явно объясняем, почему прямой доступ здесь действительно нужен.

 6. Методы boundary должны сохранять старую семантику ошибок и состояний: absent resource, backpressure, fatal error, no-op, counters и release paths не должны сливаться в один общий `bool`, если вызывающему коду важно различие.

 7. Для каждого нового boundary/API добавляем focused tests: отсутствующий ресурс, активный fake/stub, ошибка, edge-case accounting, и проверка, что метод не меняет состояние, которым не должен владеть.

 8. Не делаем косметический рефакторинг вместе с фичей. Если меняется архитектурная граница, это отдельное осознанное изменение с понятной причиной и проверками.

 9. Перед реализацией фичи кратко описываем архитектуру: какие модули владеют состоянием, какие методы являются границей, какие инварианты нельзя нарушить, какие тесты это закрепят.


 ## Правила размера модулей и формы Rust API

 1. Не раздуваем центральные модули и crate-ы. Для Pointman это особенно важно для `apps/pointman` (`main.rs` / загрузка Intro), `crates/engine` (`Simulation`), `crates/render` (`backend.rs` уже сильно больше лимита — новые Vulkan-фичи только в отдельные модули), `crates/assets` (парсеры World00p/объектов/моделей) и тонкого контракта кадра (`DrawList`, `MeshInstance`, `PointLight`, `TextureId`): новая логика должна попадать к модулю, который владеет соответствующим состоянием и инвариантами, а не в самый большой или самый удобный файл.

 2. Если файл уже близок к 700-800 строкам, новая фича по умолчанию выносится в отдельный модуль. Исключение допустимо только при маленькой локальной правке; тогда явно объясняем, почему новый модуль ухудшил бы читаемость или раздробил один связный инвариант.

 3. Новые Rust boundary/internal API должны быть самодокументирующимися на месте вызова. Не добавляем позиционные `bool`, мутные `Option`, числа или строки с неочевидным смыслом, если можно выразить смысл через `enum`, `newtype`, named method или отдельный intent-method. Если старый API вынуждает передать неочевидный литерал, добавляем короткий комментарий с именем параметра у callsite.
